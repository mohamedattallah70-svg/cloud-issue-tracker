# Lab 3 — Cloud Issue Tracker Architecture

## 1. Application Goal

The Cloud Issue Tracker is a small internal web application where users report technical problems (for example Wi-Fi or projector faults) and track them until they are resolved. In Lab 2 everything lived in browser memory, so issues disappeared on refresh and could not be shared between users. This design moves the data and the rules to a server so that issues persist and every user sees the same list.

The system is split into three layers:

| Layer | Responsibility |
|---|---|
| Frontend (browser) | Shows issues and collects user input. Sends HTTP requests and renders JSON responses. |
| REST API (Node.js + Express) | Receives requests, validates them, applies server-side rules and decides the response status. |
| Data layer | Stores issues. For now a local JSON file (`backend/data/issues.json`) accessed only through `issueService.js`; later a cloud database. |

## 2. Functional Scope

The application supports three operations:

- **Create an issue** — `POST /api/issues`
- **View all issues** — `GET /api/issues`
- **Change an issue status** — `PATCH /api/issues/{id}/status`

Out of scope for now: authentication, user roles, deleting issues, editing title/description, and cloud deployment.

## 3. Request Flow

### Create issue

```
User → Frontend form → POST /api/issues → API validation → Data layer
     ← Render created issue ← 201 + JSON ←──────────────────────┘
```

1. The user fills in title, description and priority, then clicks Submit.
2. The frontend sends `POST /api/issues` with the form data as JSON.
3. The API validates the body (title 3–100 chars, description 5–500 chars, priority is Low/Medium/High). If anything fails it stops and returns `400` with a `VALIDATION_ERROR`.
4. The data layer generates the `id`, sets `status` to `Open` and sets `createdAt`, then saves the issue.
5. The API replies `201 Created` with the complete issue as JSON.
6. The frontend adds the returned issue to the list, using the server's values.

### View issues

```
Page load → GET /api/issues → API → Data layer
          ← Render list ← 200 + JSON array ←──┘
```

1. When the page loads, the frontend sends `GET /api/issues`.
2. The API asks the data layer for every stored issue.
3. The API replies `200 OK` with a JSON array (an empty array `[]` if there are none — this is not an error).
4. The frontend renders one card per issue, or "No issues yet" when the array is empty.

### Change status

```
Button → PATCH /api/issues/{id}/status → API validation → Data layer
       ← Re-render issue ← 200 + updated JSON ←───────────────┘
```

1. The user clicks the status button on an issue.
2. The frontend sends `PATCH /api/issues/{id}/status` with a body such as `{"status": "Resolved"}`.
3. The API checks that the status is an allowed value (`Open` or `Resolved`), otherwise `400`, and that the issue exists, otherwise `404 ISSUE_NOT_FOUND`.
4. The data layer changes only the `status` field of that issue.
5. The API replies `200 OK` with the full updated issue.
6. The frontend re-renders that issue with its new status.

## 4. Trust Boundaries

```
USER-CONTROLLED SIDE                 APPLICATION-CONTROLLED SIDE

Browser input ───── HTTP request ─────▶ REST API ─────▶ Data
     ▲                                     │
     └────────── JSON response ◀───────────┘
```

**User-controlled side:** the browser, the form fields, the buttons and every HTTP request that leaves the browser. The user can change any of it using Developer Tools, curl or Postman, so every incoming request is treated as untrusted until the API has validated it.

**Application-controlled side:** the REST API and the data layer. Only our code runs here, and the data can only be reached through the API.

**The boundary is the HTTP request, and it follows these rules:**

1. The API validates every request. Frontend checks (such as `required`) are only for user convenience, never for security.
2. The browser never talks to the data layer directly.
3. The client cannot set server-owned fields: `id`, `status` on creation, and `createdAt` are always generated by the server.
4. The API returns only what the frontend needs and never leaks internal errors or stack traces; unexpected failures return a generic `500 INTERNAL_ERROR`.
5. The frontend shows issue text as plain text (`textContent`), never as HTML, to prevent script injection.
